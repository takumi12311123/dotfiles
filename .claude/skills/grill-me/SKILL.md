# Grill Me

## Purpose

**「分かったつもり」を壊す skill。**

説明を読んで頷けることと、自分で再構成できることは別物。
この skill は容赦なく問い詰めて、理解の穴を可視化する。

優しくしないこと。ただし **人格ではなく理解を攻撃する**。

## When to Use

| 使う | 使わない |
|------|---------|
| 「理解できてるか試して」 | 説明が欲しい → `explain-impl` |
| `explain-impl` の締め | 抽象度を変えたい → `eli5` |
| PR をマージする前の自己検証 | コード品質チェック → `quality-gate` |
| 他人 / AI が書いたコードを引き継ぐ前 | |

## Scope Resolution

| 引数 | 対象 |
|------|------|
| なし | 直前のセッションで扱った変更 + branch diff（下記 BASE 参照） |
| `<PR番号>` | `gh pr diff <番号>` |
| `<path>` / `<topic>` | 該当実装・概念 |

ベースブランチの解決は既存 skill (`pr-comprehend` / `quality-gate`) と揃える:

```bash
BASE=$(git merge-base HEAD origin/main 2>/dev/null || git merge-base HEAD main)
git diff "$BASE"..HEAD
```

出題前に **必ず対象を読む**。読まずに一般論クイズを出すのは禁止。

## Difficulty Ladder

出題は必ずこの順で登る。前の段で落ちたら次に進まない。

| L | 段階 | 問う内容 | 例 |
|---|------|---------|-----|
| **L1** | 想起 | 何をしたか | 「この PR で追加されたファイルは何をする？」 |
| **L2** | 応用 | 別状況でどうなるか | 「入力が空だったら何が起きる？」 |
| **L3** | 設計判断 | なぜその方法か | 「B 案ではなく A 案にした理由は？」 |
| **L4** | エッジ / 破壊 | どこで壊れるか | 「この前提が崩れる状況は？」 |

L4 まで正答できて初めて「理解した」とみなす。

## Question Format

### 出題ルール（厳守）

1. **1 回につき最大 3 問** まとめて出す（多すぎると考えずに答える）
2. **全問出し終えるまで正解を明かさない**
3. 選択式は `AskUserQuestion` で出す。選択肢は 4 つ、**正解の位置は毎回ランダム化**
   - `AskUserQuestion` が使えない場合は、インラインの番号付き選択肢で代替する
4. 選択肢は「明らかに違う」ものを混ぜない。**全部それっぽく** する
5. **記述式を最低 1 問混ぜる**（選択式だけだと勘で当たる）
   - 記述式は `AskUserQuestion` では出せないので、**通常のメッセージ本文で質問する**
   - 出し方: 選択式を `AskUserQuestion` で先に出し、同じターンのテキストで記述式を提示する
6. 出典となるコードを見せるかは問題次第。L3/L4 では見せてよい

### 問題の質

| 良い問題 | 悪い問題 |
|---------|---------|
| 分かっていないと消去法でも当たらない | 常識で解ける |
| 実際のコードの挙動に紐づく | 一般論 |
| 「なぜ」を問う | 用語の暗記 |
| 誤答が典型的な誤解に対応している | ダミーが雑 |

## Grading

全問回答後にまとめて採点する。

```markdown
## 採点
| # | レベル | 判定 | 何が問われていたか |
|---|--------|------|------------------|
| Q1 | L1 | ✅ | ... |
| Q2 | L2 | ❌ | ... |

**正答: 2/3 (L2 で失点)**

### 誤答の分析
- Q2: <選んだ答え> を選んだのは <この誤解> があるため。
  実際は <正しい理解>。根拠: `path/file.go:42`
```

**誤答は必ず「なぜそう考えたか」を推定して言語化する。**
正解を言うだけでは同じ間違いを繰り返す。

## Follow-up Routing

採点結果から次の行動を決める。

| 結果 | 次 |
|------|-----|
| L1 で失点 | `explain-impl` に戻る（前提が入っていない） |
| L2-L3 で失点 | `eli5` で該当箇所だけ抽象度を下げて再説明 → 再出題 |
| L4 のみ失点 | エッジケースを `user-scenario` で洗い出して再出題 |
| 全問正解 | 難易度を上げてもう 1 ラウンド、または終了 |

**再出題は同じ問題を出さない。** 同じ論点を別角度から問う。

## Termination

以下すべてを満たしたら終了:

- [ ] L1〜L4 各段階で正答している
- [ ] 誤答した論点について、再出題で正答している
- [ ] ユーザーが自分の言葉で「この変更の要点」を 3 行で説明できる

最後に **弱点サマリ** を出す:

```markdown
## 今回の弱点
- <論点>: <なぜ弱いか> → 次に読むと良い箇所: `path/file.go`
```

## 理解確認記録の更新 (Gate B / B')

このフェーズの結果は `.claude/pr-review/understanding-*.md` に記録する。
**形式・成立条件・照合キーは `.claude/rules/flow-gates.md` の Gate B / B' が定義**（再定義しない）。

決定的なルール:

- 各項目には **ユーザー自身の説明を引用として転記する**（`> **ユーザーの説明**: ...`）
- **AI が書いた要約で埋めるのは偽装**。ユーザーが説明していない項目に ✅ を付けない
- 開発フローは `confirmed-head`（ローカル HEAD）、レビューフローは `pr-head`（PR head）が基準
- 既に記録がある場合は上書きせず、実施した skill と項目を **追記** する

grill-me は加えて `## grill-me 結果` 節に L1〜L4 の正否と弱点、および誤答の要旨を記録する。
## Interaction Rules

- 日本語で出題・採点する (`.claude/rules/language.md`)
- 答えを誘導しない。ヒントは求められたときだけ、1 段階ずつ
- 「惜しい」で流さない。間違いは間違いと言う
- ただし煽らない。攻撃対象は理解のギャップであって人ではない
- ユーザーが「もういい」と言ったら即終了し、弱点サマリだけ残す

## Anti-patterns

| NG | 理由 |
|----|------|
| コードを読まずに出題 | 一般論クイズになり無意味 |
| 正解を毎回同じ位置に置く | パターンで当てられる |
| 1 問ごとに答え合わせ | 前問の答えが次問のヒントになる |
| 選択肢に露骨なダミー | 消去法で解けてしまう |
| 全問正解を前提に進める | 弱点が残る |
| 優しく採点する | この skill の存在意義が消える |
