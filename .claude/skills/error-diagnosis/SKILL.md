# Error Diagnosis

## Purpose

**エラー調査で一番高くつく失敗は、推測を「原因」として提示すること。**

推測のまま修正に入ると、直らないだけでなく「直したつもり」の差分が積み上がる。
この skill は **確定** と **仮説** を明確に区別し、確定に足りない情報があれば
曖昧に「ログをください」ではなく **取得方法つきで具体的に** 依頼する。

## 確定の基準（この skill の中核）

**証拠となる「観測出力」は広く取る** — アプリログに限らず、stderr / コンパイルエラー /
テスト・CI の出力 / スタックトレース / クラッシュダンプなど、実際に観測された出力すべて。

次の 3 つをすべて満たすときだけ「原因を確定した」と言ってよい:

1. **発生経路を証拠の引用で説明できる** — 観測出力（実際の出力の引用）と、コード経路が
   存在する場合はコード箇所（`file:line`）を引用し、「この入力がここを通り、ここで壊れる」を
   途切れなく辿れる
2. **その経路が観測された症状をすべて説明する** — 一部しか説明できないなら別原因が残っている
3. **矛盾する証拠が無い** — 反証となる出力・挙動が残っているうちは確定しない

1 つでも欠けるなら、それは **仮説**。仮説の扱いは次の順で決める:

1. **反証（条件 3 違反）が 1 つでもある** → 確度は付けない。**棄却**するか、反証を
   説明し直せるまで**保留**にする（保留は報告に残す。下の Step 5a）
2. 反証が無ければ、条件 1・2 の未達の組み合わせで確度が一意に決まる:

| 確度 | 未達の条件（条件 3 は満たしている前提） |
|------|--------------------------------------|
| 高 | 条件 1 のみ未達（引用が揃えば確定できる） |
| 中 | 条件 2 のみ未達（引用は揃うが症状の一部が未説明） |
| 低 | 条件 1・2 とも未達 |

3. **同格の対立仮説が残っている場合**は、上の判定から 1 段階下げる（低はそのまま）

**証拠の引用なしに「原因は〜です」と書くのは違反。**

## Process

```
Step 1: 症状の整理    → 期待 vs 実際 / 再現条件 / いつから
Step 2: 証拠収集      → ログ + コード読解（エラー文言から逆引き）
Step 3: 仮説列挙      → 各仮説に「裏付ける証拠 / 反証する証拠」を紐付け
Step 4: 検証          → 証拠と突合。足りなければ Step 5b へ
Step 5a: 確定         → 診断報告を出す
Step 5b: 情報依頼     → 不足情報を取得方法つきで依頼 → 回答を得て Step 2 へ戻る
Step 5c: 未確定終了   → 情報が入手不能 / 依頼を繰り返しても前進しないときの終端
```

### Step 1: 症状の整理

調査を始める前に 3 点を固定する。埋まらない項目は Step 5b の依頼対象。

- **期待 vs 実際**: 何が起きるはずで、実際は何が起きたか（エラー文言は原文のまま）
- **再現条件**: 常に起きるか、特定の入力・環境・タイミングか
- **いつから**: 以前は動いていたか。動いていたなら何が変わったか（`git log` で挟み撃ちできる）

### Step 2: 証拠収集

**観測出力とコードを往復する。** コード経路が存在するエラーは、片方だけでは経路を確定できない
（コンパイルエラーのように出力単体で経路が確定するものはその限りでない）。

```bash
# 1. エラー文言から出力箇所を逆引きする（変数展開部分は削って検索）
grep -rn '<エラー文言の固定部分>' --include='*.<ext>' .

# 2. スタックトレースがあれば、フレームを上から順にコードで辿る

# 3. 出力箇所から呼び出し元へ遡る
#    serena: find_symbol → find_referencing_symbols

# 4. 「動いていたのに壊れた」なら変更履歴を疑う
git log --oneline -20 -- <関連パス>
```

集めた証拠は「観測出力の引用」と「コード箇所 (`file:line`)」の形で手元に残す。
Step 5a の診断報告はこの引用だけで組み立てる。

### Step 3: 仮説列挙

**対立仮説が合理的に立つ限り、複数出す。** 1 つしか出さないと、それを裏付ける証拠だけを
探し始める（確証バイアス）。証拠が単一原因を直接指しているなら人工的な対立仮説は不要 —
その代わり **「他に有力な仮説が無い理由」を 1 行残す**。

| 仮説 | 裏付ける証拠 | 反証する証拠 | 判定 |
|------|------------|------------|------|
| 設定値が環境で違う | ログに default 値が出ている | — | 確度: 高 |
| 依存の版差 | — | lockfile は変更されていない | 棄却（反証あり） |

### Step 4: 検証

- 各仮説を証拠と突合し、未解消の反証が出た仮説は **棄却するか「保留・確度なし」にする**
  （棄却は理由を残す。保留は反証を解消するための検証か Step 5b の情報依頼を明記する）
- 再現実験ができる場合は最小再現を作って確かめる（本番相当の環境が要るなら Step 5b）
- **委譲の判断**（条件は既存ルールが定義する。ここで再定義しない）:
  - 3 ファイル超に跨る複雑バグの根本原因分析 → `.claude/rules/codex-delegation.md`（`codex-design` / Codex CLI）
  - 外部ライブラリ / 外部 API 起因の疑い → `web-research` skill（挙動仕様・既知バグの裏取り）

### Step 5a: 確定 — 診断報告

```markdown
## 診断報告

### 症状
<期待 vs 実際 / 再現条件>

### 原因（確定）
<発生経路の説明>

### 証拠
- 観測出力: `<実際の出力の引用（ログ / stderr / テスト・CI 出力など）>`
- コード: `path/to/file.go:42` — <その箇所で何が起きるか>

### 棄却・保留した仮説
| 仮説 | 区分（棄却 / 保留・確度なし） | 理由（棄却根拠 or 未解消の反証） |

### 修正方針
<方向性の提示まで。修正は開発フロー (spec-agree →) に乗せる>
```

確定に至らなかった場合も同じ形式で出すが、見出しは確度を付けられるとき（条件 3 を満たす
仮説が残っているとき）に限り **「原因（仮説・確度: 高/中/低）」** とし、確定に何が
足りないかを明記する。反証未解消のまま保留した仮説は「棄却・保留した仮説」の表に
区分 **「保留・確度なし」** で載せ、未解消の反証を理由欄に書く。残っている仮説が
**すべて保留** のときは見出しを **「原因（保留・確度なし）」** とし、保留テーブルで報告する。

### Step 5b: 情報依頼

**「ログをください」は依頼ではない。** 各項目に 3 点セットを必ず付ける:

| 欲しい情報 | 目的（どの仮説を判定するか） | 取得方法 |
|-----------|---------------------------|---------|
| 発生時刻前後のアプリログ | 仮説1「設定値の環境差」の裏付け。default 値が出ていれば裏付け証拠になる | `kubectl logs <pod> --since=1h \| grep -i 'config'` |
| 実際に読まれている環境変数 | 同上の反証確認 | `kubectl exec <pod> -- env \| grep APP_` |

- **目的** の無い依頼はしない — 何のために要るかが書けないなら、まだ仮説が整理できていない
- **取得方法** はコピペで実行できるコマンド例まで書く（環境が不明ならその確認から依頼する）
- **返し方と秘匿を指定する** — 期待する形式（出力の貼り付け / ファイル抜粋 / exit status）を書き、
  環境変数・認証情報が混ざりうる出力にはマスキングを依頼する
- 回答を得たら Step 2 に戻り、証拠として突合する。**得られた証拠は裏付けであって確定ではない** —
  確定を宣言する前に、必ず「確定の基準」3 条件を再評価する

### Step 5c: 未確定終了

依頼した情報が入手不能（権限・環境が無い、ログが既にローテートされた等）、または
**依頼 → 回答のループを 2 周しても仮説の確度が上がらない** ときは、ループを打ち切って
未確定のまま終端する。Step 5a と同じ形式で報告する（見出しは Step 5a の未確定時の規定に
従う — 確度を持つ仮説が残っていれば「原因（仮説・確度: 高/中/低）」、すべて保留なら
「原因（保留・確度なし）」）。加えて次を明記する:

- ここまでに得られた証拠と、残った仮説（確度つき。保留は区分・未解消の反証つき）
- 確定に足りない証拠と、それが得られなかった理由
- 次のアクションとオーナー（例: 監視ログの保持期間延長を運用チームへ依頼）

## Boundaries

- **修正はしない。** この skill の終端は「診断報告 + 修正方針の提示」。
  修正は通常の開発フロー（`spec-agree` → 実装。軽微でも Gate A の判断はユーザー）に渡す
- テスト作成は `test-generator`、修正後の解説は `explain-impl` の領分

## Anti-patterns

| NG | 理由 |
|----|------|
| 証拠の引用なしに「原因は〜」と断定する | 確定と仮説の混同。この skill の存在意義が消える |
| 対立仮説が立つのに 1 つだけで検証に入る | 確証バイアス。裏付けだけを探し始める |
| 情報依頼を際限なく繰り返す | 2 周で前進しなければ Step 5c で未確定のまま終端し、次のアクションを渡す |
| 「ログをください」とだけ依頼する | 何の・どの期間の・どう取るかが無いと往復が増える |
| 反証が出た仮説に確度を付けたまま進める | 棄却か保留（確度なし）にして次へ。理由を残せば手戻りしない |
| 診断の勢いのまま修正まで始める | スコープ逸脱。修正は Gate A を通す |
| エラー文言を意訳して検索する | 原文の固定部分で引かないと出力箇所に辿り着けない |
