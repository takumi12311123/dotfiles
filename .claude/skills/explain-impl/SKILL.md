# Explain Implementation

## Purpose

**「動くコードができた」と「なぜそう作ったか分かっている」は別物。** その差を埋める skill。

`pr-comprehend` は *レビュー負荷を下げる digest* を出す。
この skill は *ユーザーの頭の中に理解を残す* ことが目的なので、
一方的に説明せず「対話 + チェックリスト + 確認」で進める。

## When to Use

| 使う | 使わない |
|------|---------|
| 「この実装解説して」「なんでこうしたの？」 | 通常の実装依頼（完了報告で終わり） |
| 実装完了後の「振り返りたい」 | レビュー指摘の修正だけ |
| 他人 / AI が書いたコードを読み解きたい | PR digest が欲しいだけ → `pr-comprehend` |
| 既存機能の仕様を把握したい | 単なる API の使い方 → `latest-docs` |

## Scope Resolution

引数から対象を決める。

| 引数 | 対象 |
|------|------|
| なし | working tree + branch diff（下記 BASE 参照） |
| `<PR番号>` | `gh pr diff <番号>` |
| `<path>` | そのファイル / ディレクトリの現行実装 |
| `<symbol>` | serena `find_symbol` で定義 + 参照元を辿る |

ベースブランチの解決は既存 skill (`pr-comprehend` / `quality-gate`) と揃える:

```bash
BASE=$(git merge-base HEAD origin/main 2>/dev/null || git merge-base HEAD main)
git diff "$BASE"..HEAD
```

対象が 500 行を超える diff の場合は Gemini に要約を委譲してから読む
(`.claude/rules/gemini-delegation.md`)。

## Execution Flow

```
┌──────────────────────────────────────────────┐
│ Step 0: 対象確定 & 現状把握                    │
│   → scope resolution                          │
│   → 「まず今の理解を話して」と先に聞く          │
└──────────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│ Step 1: チェックリスト提示                      │
│   → Markdown checklist を出力し、以降維持       │
└──────────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│ Step 2: 問題の解説 (最重要)                     │
│   → 何が問題か / なぜ起きたか / 別案は何か       │
│   → 理解確認してから次へ                        │
└──────────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│ Step 3: 解決策の解説                            │
│   → 設計判断 / 却下した案 / エッジケース         │
└──────────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│ Step 4: 影響範囲と文脈                          │
│   → 誰が得をするか / 何が壊れうるか / 次の一手   │
└──────────────────────────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│ Step 5: 定着確認                                │
│   → `grill-me` に引き渡すか提案                 │
└──────────────────────────────────────────────┘
```

## Step 0: 先に聞く

**解説から始めない。** 必ず最初にこれを聞く:

> 「今の時点で、この変更が何をしているものだと理解していますか？ ざっくりで構いません」

理由: 既に分かっている部分を説明するのは時間の無駄で、
ギャップが分からないまま説明すると的外れになる。

回答から理解度を 3 段階で見立て、以降の粒度を決める。

| 見立て | 進め方 |
|--------|--------|
| ほぼ分かっている | Step 2 を圧縮し、エッジケース / 設計判断に時間を使う |
| 何をしたかは分かる、なぜかは曖昧 | Step 2 (問題) を厚く |
| 全く分からない | `eli5` レベルから入り、比喩 → 実コードの順 |

## Step 1: チェックリスト

以降のターンで毎回、更新版を再掲する。

```markdown
## 理解チェックリスト
### 1. 問題
- [ ] 何が問題だったか
- [ ] なぜその問題が起きたか（根本原因）
- [ ] 他にどんな解き方がありえたか
### 2. 解決策
- [ ] 実際に何をしたか
- [ ] なぜその方法を選んだか（設計判断）
- [ ] 想定しているエッジケース / 想定外
### 3. 文脈
- [ ] 誰にとって何が良くなるか
- [ ] この変更が壊しうるもの（影響範囲）
- [ ] 今後どこに効いてくるか
```

チェックは **ユーザーが自分の言葉で説明できたときだけ** 付ける。
「はい分かりました」ではチェックしない。

## Step 2: 問題の解説（最重要）

ここが一番大事。以下を必ずコードの実物とセットで示す。

1. **症状**: 何が起きていた / 何ができなかったか
2. **根本原因**: なぜそうなったか（設計上の前提が崩れた箇所を特定）
3. **代替案**: 少なくとも 2 つ。「なぜ却下したか」まで
4. **もし放置したら**: 何が起き続けるか

コードを見せるときは `file_path:line` 形式で引用し、
「この行が何を仮定しているか」を言語化する。

## Step 3: 解決策の解説

- diff を **意味の単位** に分割して順に説明する（ファイル順に読み上げない）
- 各単位で「これが無いとどうなるか」を必ず添える
- 設計判断は trade-off の形で示す（採用案の欠点も言う）
- エッジケース: 境界値 / 空 / 並行 / 失敗経路 / 後方互換

## Step 4: 影響範囲と文脈

- 利用者視点のシナリオが必要なら `user-scenario` skill に委譲
- 「この変更を revert したら何が戻るか」で影響範囲を検証する
- 関連する既存の設計原則 (`.claude/rules/`) との整合を示す

## Step 5: 終了条件

チェックリスト全項目が **ユーザーの説明によって** 埋まるまで終わらない。

終了前に必ず提案する:

> 「理解の抜けを潰すなら `grill-me` で口頭試問できます。やりますか？」

## 理解確認記録の更新 (Gate B / B')

このフェーズの結果は `.claude/pr-review/understanding-*.md` に記録する。
**形式・成立条件・照合キーは `.claude/rules/flow-gates.md` の Gate B / B' が定義**（再定義しない）。

決定的なルール:

- 各項目には **ユーザー自身の説明を引用として転記する**（`> **ユーザーの説明**: ...`）
- **AI が書いた要約で埋めるのは偽装**。ユーザーが説明していない項目に ✅ を付けない
- 開発フローは `confirmed-head`（ローカル HEAD）、レビューフローは `pr-head`（PR head）が基準
- 既に記録がある場合は上書きせず、実施した skill と項目を **追記** する
## Interaction Rules

- 一度に全部説明しない。1 ステップごとに区切って確認する
- 抽象度の指定 (ELI5 / ELI14 / ELII) が来たら `eli5` skill に切り替える
- 質問の出し分け:
  - **自由記述で答えてほしい質問**（Step 0 の理解確認、「自分の言葉で説明して」）は
    通常のメッセージ本文で聞く。`AskUserQuestion` は使わない
  - **選択肢で答えられる質問**（理解度チェックの二択・多肢選択）は `AskUserQuestion` を使い、
    選択肢順はランダム化する。使えない場合はインラインの番号付き選択肢で代替
- 応答は日本語 (`.claude/rules/language.md`)

## Anti-patterns

| NG | 理由 |
|----|------|
| diff をファイル順に読み上げる | 意味の単位ではないので頭に残らない |
| 「なぜ」を飛ばして「何を」だけ話す | 応用が効かない |
| 理解確認せず次に進む | 積み上がらない |
| 一度に全ステップ出力する | 読み飛ばされる |
| 代替案を示さない | その選択が良い理由が測れない |
