# User Scenario

## Purpose

**コードは「どう動くか」しか書いていない。「誰が、何のために、どう使うか」は書いていない。**

この skill はコードから利用者視点のシナリオを復元し、
- 仕様の理解（何が正しい振る舞いか）
- 仕様の穴（誰も決めていない振る舞い）
- テスト観点（`test-generator` への入力）

を同時に得る。

## When to Use

| 使う | 使わない |
|------|---------|
| 「この機能どう使われるの？」 | コードの内部構造を知りたい → `explain-impl` |
| 仕様書が無い実装の仕様を起こしたい | PR レビュー digest → `pr-comprehend` |
| 受け入れ基準 / テスト観点を作りたい | テストコードを書く → `test-generator` |
| 他人 / AI が書いた変更の妥当性を測りたい | ライブラリの使い方 → `latest-docs` |

## Scope Resolution

| 引数 | 対象 |
|------|------|
| なし | branch diff（下記 BASE 参照） |
| `<PR番号>` | `gh pr diff <番号>` |
| `<path>` / `<feature名>` | 該当実装を辿って全体を対象にする |

ベースブランチの解決は既存 skill (`pr-comprehend` / `quality-gate`) と揃える:

```bash
BASE=$(git merge-base HEAD origin/main 2>/dev/null || git merge-base HEAD main)
git diff "$BASE"..HEAD
```

## Execution Flow

```
┌────────────────────────────────────────────┐
│ Step 1: アクター抽出                         │
│   → 誰がこのコードを起動するか               │
└────────────────────────────────────────────┘
                  ↓
┌────────────────────────────────────────────┐
│ Step 2: トリガーと目的の特定                  │
│   → いつ / 何を達成したくて叩くか            │
└────────────────────────────────────────────┘
                  ↓
┌────────────────────────────────────────────┐
│ Step 3: シナリオ化 (Given-When-Then)         │
│   → ハッピーパス / 異常系 / エッジ            │
└────────────────────────────────────────────┘
                  ↓
┌────────────────────────────────────────────┐
│ Step 4: 仕様の穴を検出                        │
│   → 未定義 / 暗黙の前提 / 矛盾               │
└────────────────────────────────────────────┘
                  ↓
┌────────────────────────────────────────────┐
│ Step 5: 受け入れ基準に落とす                  │
│   → チェック可能な形 + テスト観点            │
└────────────────────────────────────────────┘
```

## Step 1: アクター抽出

コードの入口 (エントリポイント) から遡って、実際に叩く主体を列挙する。

- エンドユーザー（UI 操作 / CLI 実行）
- 別サービス / 別スクリプト（API・イベント）
- 開発者・運用者（セットアップ、障害対応）
- スケジューラ / CI（自動実行）

**「人間だけがアクターではない」**。cron や他 skill も列挙する。

## Step 2: トリガーと目的

各アクターについて 1 行で書く:

> `<アクター>` は `<状況>` のとき、`<目的>` のために `<操作>` する

目的が書けないアクターは、**そもそも必要かどうか**を疑う。

## Step 3: シナリオ化

最低限この 3 分類を埋める。

```markdown
### S1: <シナリオ名>  [happy]
- **Given**: 前提状態
- **When**: 操作
- **Then**: 期待結果（観測可能な形で）
- **根拠**: `path/to/file.go:42`
```

| 分類 | 必ず考えること |
|------|---------------|
| happy | 一番よくある成功経路。1 本に絞る |
| error | 入力不正 / 権限なし / 依存先が落ちている / タイムアウト |
| edge | 空・0件・上限・同時実行・再実行 (冪等性) / 途中失敗後の再開 |

**Then は観測可能に書く。** 「正しく処理される」は不可。
「終了コード 0 かつ `~/.claude/skills` が symlink になっている」のように書く。

各シナリオに **根拠となるコード位置** を必ず添える。
根拠が示せないシナリオは推測なので `[推測]` と明示する。

## Step 4: 仕様の穴を検出

シナリオを書くと必ず「どうなるのが正解か決まっていない」ものが出る。それが価値。

| 種別 | 見つけ方 |
|------|---------|
| 未定義 | エラー分岐が無い入力パターン |
| 暗黙の前提 | コードが暗黙に仮定している環境・順序・状態 |
| 矛盾 | 同じ入力に対し別経路で別の結果になる |
| 責務漏れ | どのアクターの責任か決まっていない後始末 |

出力形式:

```markdown
### 仕様の穴
| # | 箇所 | 未定義な振る舞い | 影響 | 決めるべき人 |
|---|------|-----------------|------|-------------|
```

**ここは勝手に埋めない。** 実装で決め打ちせず、ユーザーに判断を仰ぐ。

## Step 5: 受け入れ基準

シナリオを検証可能な形に変換する。

```markdown
### 受け入れ基準
- [ ] AC1: <条件> のとき <結果> になる  (← S1)
- [ ] AC2: ...
```

そのまま `test-generator` に渡せる粒度にする。
既存テストがある場合は **カバーされていない AC** を明示する。

## Output

- **対話内で提示するのが基本**（ファイルは作らない）
- 分量が多い / 再利用したい場合のみ `.claude/pr-review/scenario-<slug>.md` に保存する。
  保存する場合は `pr-comprehend` と同じ前提準備を **この skill 側で実行してから** 書く:

```bash
GIT_DIR=$(git rev-parse --git-dir) || exit 1
EXCLUDE_FILE="$GIT_DIR/info/exclude"
mkdir -p "$(dirname "$EXCLUDE_FILE")" && touch "$EXCLUDE_FILE"
grep -qxF '.claude/pr-review/' "$EXCLUDE_FILE" || echo '.claude/pr-review/' >> "$EXCLUDE_FILE"
mkdir -p .claude/pr-review
```

## 理解確認記録の更新 (Gate B / B')

このフェーズの結果は `.claude/pr-review/understanding-*.md` に記録する。
**形式・成立条件・照合キーは `.claude/rules/flow-gates.md` の Gate B / B' が定義**（再定義しない）。

決定的なルール:

- 各項目には **ユーザー自身の説明を引用として転記する**（`> **ユーザーの説明**: ...`）
- **AI が書いた要約で埋めるのは偽装**。ユーザーが説明していない項目に ✅ を付けない
- 開発フローは `confirmed-head`（ローカル HEAD）、レビューフローは `pr-head`（PR head）が基準
- 既に記録がある場合は上書きせず、実施した skill と項目を **追記** する

`user-scenario` が主に埋めるのは「影響範囲 / 誰に何が良くなるか」。
合意済み仕様がある場合は **spec の受け入れ基準との差分** も記録する。
## Anti-patterns

| NG | 理由 |
|----|------|
| 関数単位でシナリオを書く | それは単体テストであって利用者視点ではない |
| happy path だけ書く | 一番バグるのは異常系 |
| Then が「正しく動く」 | 検証できない |
| 仕様の穴を勝手に埋める | 実装者の推測が仕様として固定される |
| コード根拠を書かない | 幻覚シナリオと区別できない |
