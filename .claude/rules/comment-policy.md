# Comment & Context Policy

**セッションを見ていない人が読む** — これが唯一の前提。
コードコメント / commit message / PR description / PR コメントのどこに何を書くかを、この文書が単独で決める。
各 skill・command はここを参照し、判断基準を再定義しない。

## The Stranger Test（唯一の判定基準）

> **この会話も、この PR も見ていない人が、1 年後にこの文章だけを読んで意味が通るか？**

通らないなら、それは **セッション文脈依存** のテキスト。
コードにも PR description にも入れてはいけない。行き先は PR コメント (`prr`) か、削除。

## 4 つの置き場所

| 置き場所 | 寿命 | 読者 | 書くもの |
|---------|------|------|---------|
| **コードのインラインコメント** | コードが消えるまで永続 | 未来の保守者（文脈ゼロ） | **今のコードがなぜこの形なのか**。制約・不変条件・落とし穴・非自明な理由 |
| **commit message** | 永続（`git log` / `blame` から辿られる） | 将来の調査者 | この commit が**何を変えたか + なぜ**。1 commit = 1 論理単位 |
| **PR description** | 永続（`blame` → PR で辿られる） | レビュア + 将来の考古学者 | **PR 単体で自己完結した**背景・課題・変更内容・影響範囲・検証方法 |
| **PR コメント (`prr`)** | レビュー期間中の一時的なもの | 今このレビューをしている人 | レビューを助ける説明、判断の経緯、「ここ見て」の案内、会話の続き |
| **（どこにも書かない）** | — | — | 差分を読めば分かること、コードを読めば分かること |

## 決定木

```
その文章は…
│
├─ コードを読めば分かる？ ─────────────────── YES → 書かない
│
├─ 「変更という出来事」を語っている？
│   （〜に変更した / 以前は〜だった / 〜を追加した）
│   │
│   ├─ YES → コードコメントは禁止。
│   │        マージ後も価値がある → commit message / PR description
│   │        レビュー中だけ価値がある → PR コメント (prr)
│   │
│   └─ NO（コードの「現在の姿」を語っている）
│       │
│       ├─ 非自明な理由・制約・落とし穴がある → コードのインラインコメント ✅
│       └─ 自明 → 書かない
│
└─ 読者は「今このレビューをする人」だけ？ ──── YES → PR コメント (prr)
```

### 最重要の非対称性

**コードコメントは「変更」を語ってはいけない。**
コードは変更の履歴ではなく **現在の状態** を表す。
「〜に変更した」「以前は〜だった」「今回〜に対応」は git が既に持っている情報で、
コードに書くと次の変更で必ず腐る。**変更の話は git（commit / PR）に置く。**

## 禁止パターン（コードコメント）

| 種別 | 例（NG） | 対処 |
|------|---------|------|
| 会話参照 | `// ご要望どおり 30 秒に変更`, `// as requested` | 削除。理由が非自明なら下の書き換えへ |
| レビュー参照 | `// 指摘対応`, `// レビューで指摘されたため`, `// per review feedback` | 削除 → 必要なら PR コメント |
| 差分の実況 | `// 今回追加`, `// 〜から変更`, `// previously returned null`, `// no longer used` | 削除（git が持っている） |
| セッション時制 | `// 先ほどの修正`, `// さっき直した箇所`, `// 一旦こうしておく` | 削除 |
| コードの読み上げ | `// i をインクリメント` (`i++` の上) | 削除 |
| 死んだコード | コメントアウトされた実装 | 削除 |
| AI メタ | `// TODO(claude)`, `// 私がこれを追加した理由は` | 削除 |
| 宛先違い | `// この関数は〜という設計にしたので確認してください` | PR コメント (`prr`) へ移す |

### 生き残ってよいコードコメント

- **WHY**: 非自明な理由・制約・トレードオフ（`// 30s: 上流 API が 25s でタイムアウトするため`）
- **不変条件 / 前提**: `// 呼び出し元でロック済みであること`
- **落とし穴**: `// この API は 204 でも body を返すことがある`
- **公開 API のドキュメント**: godoc / JSDoc / docstring
- **ライセンスヘッダ**、理由付き `TODO` / `FIXME`（追跡先つき）

## 書き換えレシピ（削除ではなく救済したいとき）

| Before（セッション依存） | After（文脈フリー） |
|------------------------|-------------------|
| `// ご指摘のとおり 30s に変更` | `// 30s: 上流 API のタイムアウト 25s + マージン` |
| `// 今回 null チェックを追加` | `// listAll() は該当なしで null を返す（空配列ではない）` |
| `// 前は同期版だったが非同期にした` | `// 呼び出し元の UI スレッドを塞がないため非同期` |
| `// 一旦リトライ 3 回` | `// リトライ 3 回: SLA 99.9% を満たす最小回数（計測値）` |
| `// レビューで言われた仕様` | （仕様の根拠を書けないなら削除して PR コメントへ） |

**判定**: 書き換えた結果が「変更の話」ではなく「現在のコードの理由」になっていれば OK。

## PR description の規約

PR description は **PR 単体で自己完結** していなければならない。

### 禁止

| NG | 理由 |
|----|------|
| 「ご要望どおり対応しました」「依頼された件です」 | 依頼を知らない読者に意味不明 |
| 「レビュー指摘を反映」「前回の指摘の対応」（内容なし） | 何が変わったのか分からない |
| 「先ほどの議論のとおり」「相談した方針で」 | 会話は PR に存在しない |
| 「AI が生成した実装を修正」等のセッション実況 | 読者に無関係 |
| 「〜については別途」（リンクなし） | 追跡不能 |
| 変更の理由が書かれておらず、差分の羅列だけ | description の存在意義がない |

### 必須構成（プロジェクトの PR テンプレートがある場合はそちらが優先）

```markdown
## 背景 / 課題
（この PR を読む人が前提知識ゼロで理解できる説明。何が問題で、なぜ今直すのか）

## 変更内容
（何をどう変えたか。差分の羅列ではなく、意味の単位で）

## 影響範囲
（壊れうるもの、挙動が変わるもの、移行が必要なもの）

## 検証方法
（レビュアが再現できる手順。実行していないなら「未検証」と正直に書く）

## 既知の制約 / 今後
（あれば。無いなら節ごと省略）
```

**レビュー中のやり取り・判断の経緯は description に追記しない。** それは PR コメント。

## PR title の規約

title も永続面。`git log` のマージコミットと PR 一覧に残り、会話を知らない人が最初に読む。

| NG | OK |
|----|-----|
| `fix: address review feedback` | `fix: handle expired refresh token` |
| `chore: 指摘対応` | `chore: pin actions/checkout to v4` |
| `feat: ご要望の実装` | `feat: add CSV export to billing report` |

英語 conventional commit 形式、50 文字以内、**内容で書く**。

## commit message の規約

- subject は「何をしたか」を英語 conventional commit で（`feat: add retry to token refresh`）
- body は「なぜ」。会話参照 (`as requested`) と実況 (`review 対応`) は禁止
- 「レビュー指摘の修正」を単独 commit にする場合も、**内容で書く**
  （NG: `fix: レビュー対応` → OK: `fix: handle null from listAll()`）

## PR コメント (`prr`) に置くもの

ここが **セッション文脈の正しい行き先**。

- 「なぜこの実装にしたか」のレビュア向け解説（コードに残すほど普遍的でないもの）
- 「ここは意図的にこうしている、見てほしい」の案内
- 代替案の検討結果、却下理由
- 「この部分は次の PR で消える」等の一時的な事情
- AI が書いた箇所の注意喚起

**投稿は必ずユーザーが行う。** AI は `prr` のレビュー補足コメントを自動投稿しない（下書きを渡すまで）。

例外（`/pr` の update path）: PR 更新を知らせる `gh pr comment` は、
**ユーザーの確認を取ってから** 投稿してよい。ただし内容は実況禁止のルールに従う
（NG:「レビュー指摘を反映しました」/ OK:「listAll() の null を扱うよう修正。影響: 認証経路のみ」）。

## 適用

すべて `context-hygiene` skill が実行する（`quality-gate` / `/commit` / `/pr` / `/push` から発火、BLOCKING）。

| 面 | いつ |
|----|------|
| コードコメント（追加分・未コミット含む） | commit 前 / PR 前 |
| commit message（草案） | commit 前 |
| PR description / PR title（投稿前の下書き） | PR 作成・更新前 |
| 移送先の `prr` 下書き生成 | 上記で `MOVE` 判定が出たとき |

**この policy が拾わない範囲**: 既に merge 済みの履歴、diff に現れない既存コメント、
散文ドキュメント（Markdown / CHANGELOG）。これらは人間のレビューに委ねる。
